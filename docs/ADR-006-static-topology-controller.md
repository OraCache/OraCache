# ADR-006. Публикация статической топологии

Статус — предложено. Связанные задачи #46 и #82.

Оператор передаёт зарегистрированные регионы, ноды и политику RF. Scheduler решает размещение независимо по регионам. Граф ёмкостей учитывает уникальность ноды в партиции, заданную зональную anti-affinity и статические лимиты. Среди полных планов оптимизируется число сохранённых назначений. Порядок выбора стабилен. Полное пространство партиций продукта — 128. Для существующих PoC Snapshot сохраняет настроенное число партиций.

Controller публикует только явные намерения оператора. CLI записывает план под идентификатором, вычисленным от его содержимого. Один Controller обрабатывает очередь после выборов etcd. В одной транзакции он проверяет ключ выборов вместе с lease и create revision, ModRevision опубликованного снимка, идентичность ожидающего запроса, а затем записывает результат и при необходимости новую топологию. Публикация и результат переживают потерю ответа. Повтор применённого намерения возвращает сохранённый результат. Эквивалентный снимок сохраняет прикладную ревизию.

Снимки desired и live-view читаются одной транзакцией. Отдельный статус показывает расхождения по готовым репликам, лидеру и term. Heartbeat и истечение lease меняют live-view. Статические назначения остаются явными. План по другому составу доступен для просмотра. Для публикации такого изменения требуется подтверждённый состав и готовность Raft. Изменение master-роли требует принятой процедуры promotion и write fencing.

## Что требуется согласовать

Предложение Саши для Егора по #73 и #80. Согласовать стабильный ID операции и ответ на повтор, способ чтения подтверждённого состава с привязкой к инкарнации группы и критерии learner → готова → voter. В совместном тесте теряем ответ после изменения состава, перезапускаем CP и сверяем группу. Состав меняется ровно один раз. До подтверждённого догона реплика не получает клиентский трафик. После повышения в подтверждённом составе проверяем контрольное значение. #84 проверяет сохранение назначения, прогресс и повтор на заглушке после согласования контракта. #85 исполняет этот же сценарий на живом Raft через Dispatcher.

Предложение для #72 и #78. Привязать допуск B к измеряемой позиции репликации и проверенному догону контрольной записи с подтверждением готовности локальной группы. Согласовать порог отставания, снятие допуска при потере свежести и поведение при смене лидера B. Общий тест начинает с B, который догоняет изменения A. Gateway открывает локальное строгое чтение после подтверждённого критерия и перестаёт его выдавать при нарушении критерия.

Сценарий #83 проходит локально с остановкой лидера. На общем стенде Саша и Иван подтверждают холодный запуск, чтение уже подтверждённой версии после смены лидера и новую запись через прежний адрес Gateway.

CP API с etcd сохраняет диагностику Raft в B, но не публикует клиентские маршруты чтения для этого региона до согласования допуска.
