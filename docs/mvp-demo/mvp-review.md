# Готовность OraCache к защите MVP и план финального этапа

В `main` на 27.11.2026 (`d9414d1`) из пяти базовых требований реализованы **версионирование, репликация между двумя логическими регионами и метрики hit rate и задержки**. Готовы операции кеша для cache-aside, включая условное заполнение после `MISS`. Для завершения базового сценария нужны приложение с тестовой БД и заменяемая подписка на её изменения. Срок сдачи — **22.01.2027**. [Исходная постановка](../initial-task.md), [критерии приёмки](../acceptance-criteria.md)

На промежуточной защите можно показать запись в одном регионе, чтение тех же версий во втором и доставку накопленных изменений после паузы. На отдельном стенде Gateway можно показать смену Raft-лидера без изменения адреса клиента и графики hit rate и p95/p99.

## Готовность требований

| Требование | Статус | Реализация и границы |
| --- | --- | --- |
| Cache-aside и заполнение после `MISS` | Частично | CLI и API позволяют вручную показать `MISS → Put → HIT`. Кеш хранит непрозрачные байты. Тестовый клиент, который при `MISS` сам читает БД и заполняет кеш, предстоит добавить. [API](../../proto/cache/gateway.proto), [CLI](../../README.md#запросы-через-gateway) |
| Версионирование и условная запись | Реализовано | `Put` выдаёт возрастающий `rev` в Raft-группе; доступны чтение и удаление отдельных версий. Есть предел 10 КиБ, лимит числа версий и настраиваемый бюджет Store. При межрегиональной доставке сохраняются исходные номера версий. [Store](../../internal/store/store.go), [применение реплики](../../internal/store/replication.go) |
| Защита от отката старой версии | Частично | `expected_rev` отсеивает конкурирующие записи с одинаковой ожидаемой версией. После удаления или вытеснения ключа запоздавший клиент с `expected_rev=0` может вернуть в кеш устаревший результат из БД. Номер `rev` отсчитывает изменения кеша. [Условная запись и удаление](../../internal/store/store.go) |
| Событийная инвалидация, заменяемый источник pub/sub | Не реализовано | Есть `Delete` и доставка изменений самого кеша между регионами. Подписка на изменение профиля в источнике и обработка потерянных событий БД отсутствуют. [Протокол репликации](../../proto/replication/v1/replication.proto), [требование заказчика](../initial-task.md#инвалидация) |
| Настраиваемый TTL | Не реализовано | Поля сроков жизни объявлены в API. В рабочем Store вытеснение зависит от числа версий и бюджета, истечение по времени отсутствует. TTL heartbeat определяет доступность ноды. [API](../../proto/cache/gateway.proto), [Store](../../internal/store/store.go) |
| Репликация между двумя регионами | Реализовано для базового MVP | Две Raft-группы по три ноды, поток A → B и чтение напрямую с лидера B. Передаётся текущий набор версий ключа, пустой набор удаляет ключ. [Compose](../../compose.replication.yaml), [состояние репликации](../../internal/node/replication_state.go), [Docker E2E](../../integration/e2e/replication_test.go) |
| Модель свежести | Частично | Внутри группы доступны строгие чтения через ReadIndex. Между группами передача асинхронная с повторной доставкой и упорядоченным применением. Нужно зафиксировать условия сходимости и поведение клиента при отставании, отказе и потере состояния. Отставание от БД пока невозможно измерить. [Raft](../shardraft.md#чтения-и-ошибки-маршрутизации), [поток](../../internal/replication/state.go) |
| Топология и встроенная балансировка | Частично | Control Plane описывает несколько регионов, Gateway автоматически выбирает партицию и лидера и переключается при смене лидера. Штатная репликация настроена на одну партицию и один целевой регион, двухрегиональный Compose работает напрямую с нодами. Выбор региона при отказе и работа произвольного числа регионов требуют проверки и доработки. [Маршрутизатор](../../internal/gateway/router.go), [двухрегиональный стенд](../../compose.replication.yaml) |
| Прогрев перед допуском ноды | Частично | Learner получает журнал или snapshot и исключён из готовых клиентских реплик до повышения. Остаются приёмка необходимого набора данных и проверка доли `MISS` при подключении ноды под нагрузкой. [Тест через Gateway](../../cmd/api-gateway/membership_integration_test.go) |
| Персистентность | Не реализовано | Данные, Raft-журнал, snapshots и состояние межрегионального потока находятся в памяти. Живой кворум позволяет восстановить копию на новой ноде. Перезапуск с прежним ID требует дискового восстановления. [Raft-хранилище](../../shardraft/instance.go), [формат checkpoint](../../internal/node/statemachine.go) |
| Hit rate и p95/p99 | Реализовано для серверных RPC | Gateway и Storage Node измеряют одиночные GET/PUT/DELETE. Grafana показывает долю `HIT` среди `HIT`, `MISS` и `VERSION_NOT_FOUND` успешных GET и перцентили времени серверного обработчика. Метрики Gateway и Storage Node учитывают разные границы одного запроса. [Метрики](../../internal/cpmetrics/prometheus.go), [дашборд](../../configs/monitoring/grafana/dashboards/oracache-real.json) |
| Доля устаревших ответов, выигрыш от кеша и целевая нагрузка | Не реализовано | Остаются сверка с версией источника, измерение клиентской задержки и обращений к БД, генератор нагрузки и сохранённые сравнительные прогоны **10 000 чтений/с и 500 записей/с** с записью **10 КБ**. [Метрики и нагрузочная приёмка](../acceptance-criteria.md#метрики-и-нагрузочная-приёмка) |
| Chaos-тесты и консистентность | Частично | Есть выборы нового лидера в обеих группах, доставка накопленных изменений после паузы региона B, потеря связи с CP и потеря кворума. Остаются отказ всего региона A через региональные Gateway, контролируемая задержка WAN, потеря событий источника и восстановление после потери памяти. [Локальные тесты](../../internal/node/replication_cluster_test.go), [Docker E2E](../../integration/e2e/replication_test.go), [мониторинг отказов](../../integration/e2e/check-observability.sh) |
| Тестовый профиль | Частично | В proto есть `Profile` с полом, возрастом, городом и датой регистрации. Фамилия, имя и отчество объединены в `full_name`. Для испытаний нужны отдельные поля в синтетических данных и контролируемый размер payload. [Profile](../../proto/cache/gateway.proto), [поля по постановке](../initial-task.md#структура-данных-для-тестирования) |
| Сдача и воспроизводимость | Частично | Есть исходники, README, схемы, ADR, CI и автоматические тесты отдельных стендов. Нужны чистый запуск общего стенда, итоговый дизайн-документ с гарантированным поведением, отчёт по нагрузке и свежести и описание вклада. Публичная доступность снимка и личные вклады требуют подтверждения команды. [README](../../README.md), [схема](../architecture.html), [формат сдачи](../initial-task.md#в-каком-виде-загрузить-результат) |

Межрегиональный `Put` подтверждается после локального Raft commit/apply. Пока B недоступен, A хранит изменения в очереди и продолжает принимать записи до её лимита. После заполнения следующий `Put` или `Delete` получает `ResourceExhausted`. B отклоняет клиентские записи. Очередь хранит ключи и отправляет актуальные версии на момент чтения, поэтому промежуточные состояния могут схлопываться. Вытеснение другого ключа при `Put` отдельно в очередь не ставится. Сходимость при вытеснениях и восстановление B после полной потери памяти требуют отдельной проверки и механизма сверки. [Очередь и применение](../../internal/replication/state.go), [модель кеша](../../internal/node/statemachine.go), [sender](../../internal/replication/sender.go)

Из дополнительных функций есть вытеснение по давности записей. Stale-while-revalidate, защита от stampede, репликация только горячих ключей, адаптивный TTL и TinyLFU/ARC пока отсутствуют. Проект использует `etcd/raft`, а Store, маршрутизация, управляющий слой и межрегиональный поток реализованы в репозитории. [Store](../../internal/node/statemachine.go), [зависимости](../../go.mod)

## Что показать на промежуточной защите

### 1. Два региона и восстановление доставки

```sh
docker compose -f compose.replication.yaml up -d --build
docker compose -f compose.replication.yaml ps
```

В регионе A клиентские порты `28091–28093`, в B — `29091–29093`. Найдите лидеров по `Role` и `Ready` на HTTP `/status` (порты `28191–28193` и `29191–29193` соответственно). В каждом регионе используйте gRPC-адрес его лидера в `ORACACHE_ENDPOINT`.

1. Запишите два значения одного ключа в A и сохраните `rev` из ответов. Прочитайте обе версии в B через `get --rev` и сверьте номера и данные.
2. На B подождите, пока первый ключ доступен, затем выполните `docker compose -f compose.replication.yaml pause b-1 b-2 b-3`. Удалите первый ключ и запишите второй в A. Выполните `unpause b-1 b-2 b-3` в том же Compose-проекте. Дождитесь `MISS` для первого ключа и `HIT` для второго в B. При перевыборах снова определите лидера.
3. Для автоматического показа запустите `GOWORK=off go -C integration/e2e test -tags=e2e -count=1 -v -timeout=10m -run '^TestRegionReplication$' .`. Этот тест сравнивает версии и проверяет доставку записей и удаления после паузы B. [Сценарий теста](../../integration/e2e/replication_test.go)

У этого стенда клиент обращается напрямую к лидерам. Встроенную маршрутизацию показывает следующий стенд.

### 2. Gateway и смена лидера

```sh
docker compose -p oracache-real -f compose.cp.yaml up -d --build
curl -fsS http://127.0.0.1:9466/routes
```

Выполните `MISS → Put --expected-rev=0 → HIT` через `127.0.0.1:28080` и повторите условный `Put`, чтобы получить `CONFLICT`. Остановите контейнер лидера из `write_routes["0"].NodeID` в этом Compose-проекте. Когда появился новый лидер, через прежний адрес прочитайте подтверждённое значение и выполните новый `Put`. Дополнительно можно показать `membership get` или тест добавления, повышения и замены реплики. [Команды CLI](../../README.md#запросы-через-gateway), [команды membership](../../README.md#управление-составом-raft)

Для показа метрик добавьте `-f compose.cp-observability.yaml` к команде запуска. Откройте `http://127.0.0.1:3000/d/oracache-real-cluster` и выполните серию запросов после первого scrape. После следующего scrape на дашборде доступны hit rate, p95/p99 и состояние Raft-реплик. [Мониторинг реального кластера](../../README.md#мониторинг-реального-кластера)

### Резерв без Docker

```sh
GOWORK=off go test -race -count=1 -v ./internal/node \
  -run '^TestCrossRegionReplication'
GOWORK=off go test -race -count=1 -v ./cmd/api-gateway \
  -run '^(TestGatewayRoutesRealRaftThroughLeaderAndControlPlaneLoss|TestMembershipThroughGatewayAndCPProjection)$'
```

В этих тестах работают реальные локальные gRPC/Raft-соединения. Для ручной демонстрации используйте `../../compose.replication.yaml` и `compose.cp.yaml`, которые собираются через `Dockerfile.cp`. У отдельного `compose.storage.yaml` свой Dockerfile, в котором отсутствуют `COPY` для зависимостей `internal/membershipapi` и `internal/cpmetrics`. [Dockerfile.storage](../Dockerfile.storage), [импорты ноды](../internal/node/node.go), [импорты membership](../internal/node/membership_grpc.go), [Dockerfile.cp](../Dockerfile.cp)

## Результаты проверки

- Тесты корневого модуля и CLI прошли с `-race`, сгенерированные API компилируются. В корневом модуле прошли локальные проверки репликации, membership и серверных счётчиков и гистограмм.
- Docker E2E `TestRegionReplication` прошёл оба сценария. Сверены номера и байты версий, удаление и доставка отложенных изменений после паузы всех трёх нод региона B. [Тест](../../integration/e2e/replication_test.go)
- Docker E2E `TestControlPlaneGatewayFailover` подтвердил переход с `node-1` на `node-3` через прежний адрес. Получена прежняя версия, затем запись продвинула `rev` с 1 до 2 при той же ревизии топологии. [Тест](../../integration/e2e/cp_gateway_test.go)
- Возможности Prometheus и Grafana сверены по коду и конфигурации. Запуск мониторингового стенда в этот прогон не входил.
