# RFC-001: версии, заполнение кэша и конкурентные обновления

Статус: открыт. Область: контракт target и выбор состава MVP. Основания E-005, E-006, E-008, E-009. Этот RFC не выбирает окончательный алгоритм.

## Проблема и пользовательский сценарий

Приложение работает по cache-aside: [после MISS читает БД и заполняет кэш](../REQUIREMENTS.md#r-001). Между чтением БД и заполнением другой запрос может изменить данные. Если первый запрос придёт последним, кэш сохранит устаревшее значение как новое. Для выбора алгоритма нужно определить [допустимую свежесть и обязанности приложения](../REQUIREMENTS.md#r-009), включая поведение при сбое между изменением БД и уведомлением кэша.

Отдельная задача — предсказуемая история. Клиент должен понимать, какие версии сохранены, что означает latest и что произойдёт после удаления текущей версии. Ограниченная история принятых кэшем значений не гарантирует сохранение каждого состояния БД.

Цель RFC — выбрать проверяемый клиентский контракт этих операций и повторов. Формат дискового журнала и алгоритм переноса шардов находятся за его границами; с ними требуется согласовать срок хранения служебных метаданных.

## Понятия и установленные ограничения

**Версия кэша** назначается кэшем при новом Put. **Ревизия источника** описывала бы порядок изменений БД, но приложение не обязано предоставлять монотонный внешний счётчик. [Обязательный счётчик БД и строгая сериализация всех обновляющих Put отвергнуты](../REQUIREMENTS.md#r-010); обсуждение клиентского API в целом этим не запрещено. E-008.

**CAS** — условная запись по ожидаемой ревизии кэша. Она сравнивает состояние кэша с ожиданием клиента, но не определяет, какое прочитанное из БД значение свежее. **Lease** — ограниченное по времени право выполнить заполнение; **fillToken** может обозначать это право в запросе. **OperationID** — устойчивый идентификатор одной логической операции для распознавания повторов. Эти сущности решают разные задачи.

Установлено намерение [Get выбранной/latest версии со списком сохранённых версий](../REQUIREMENTS.md#r-006) и [настраиваемой глубиной истории](../REQUIREMENTS.md#r-007). [Delete должен удалять конкретную версию](../REQUIREMENTS.md#r-008). Точный ответ Get и семантика latest после удаления current ещё требуют согласования. E-005.

## Экспериментальная база

В срезе `f49c2502d0dda53b56d0cadfa321312122e00095` GetResponse возвращает одно значение с Rev/LatestRev без history list. Delete(rev=0) удаляет весь ключ, а удаление последней отдельной версии может открыть предыдущую. CAS реализован, но устойчивой дедупликации по operationID нет. Это факты PoC, не выбранный target-контракт. E-006, E-009.

Для Get, Put и Delete отказ `NOT_LEADER` до передачи команды в Raft допускает повтор; адрес из ответа используется только для назначенной реплики. При `Unavailable` gateway может повторить любую из трёх операций. Для записи это неоднозначный исход: потеря ответа не означает, что Put или Delete не применился. При `DeadlineExceeded` отдельной попытки можно повторить Get, но не Put или Delete. Все повторы ограничены числом попыток и общим сроком запроса. Это политика [интеграционного среза](https://github.com/OraCache/petruekhin-vibe/blob/70c07350dc473b171945f40794e21fb4522dcf2e/internal/gateway/forwarder.go), а не гарантия будущего API.

Если безусловный Put применён, а ответ потерян, повтор может создать ещё одну версию. Условный повтор после успешной первой записи может вернуть CONFLICT. В таком случае клиент всё ещё не знает исход первой попытки. Существующие bounded retries не обеспечивают exactly-once.

## Варианты интерфейса истории и удаления

Варианты в таблице — предмет этого RFC. Их перечисление не означает, что команда уже рассмотрела и отвергла каждый из них.

| Вопрос | Варианты | Цена и критерий выбора |
|---|---|---|
| Список версий | Значение и metadata списка в одном ответе; либо отдельный history endpoint | Единый ответ соответствует установленному намерению и может дать один согласованный срез. Отдельный endpoint требует согласовать отступление и поведение при изменении истории между вызовами. |
| Удаление current | latest становится MISS, старые доступны только явно; либо latest становится предыдущая версия | Первый вариант требует маркера отсутствия текущего значения и правил его жизни. Второй соответствует PoC, но расходится с высказанным намерением и требует явного согласования. |
| Удаление ключа целиком | Ограничиться `Delete(key, version)`; либо добавить отдельную операцию для всего ключа. Для `Delete` номер версии обязателен. | Нужно различить удаление версии, полное удаление и инвалидацию текущего значения с сохранением истории. Для отсутствующей версии нужен определённый результат. |

Маркер удаления (tombstone) — служебная запись о том, что значение больше не должно считаться текущим. Если такой маркер исчезает раньше, чем могут вернуться старые данные, возможно нежелательное восстановление удалённого состояния. Поэтому его срок жизни зависит от повторов, TTL, вытеснения и восстановления.

## Варианты согласования с БД

**Инвалидация после commit.** [Событийная инвалидация](../REQUIREMENTS.md#r-025) требует реакции кэша на изменение источника, и заменяемого источника событий, но не выбирает транспорт и протокол доставки. Приложение сообщает о завершившемся изменении БД, кэш сбрасывает пригодность текущего значения. Успех зависит от доставки уведомления и от того, какие задержанные заполнения допускаются после него. Нужно описать порядок уведомления, заполнения и повторов.

**BeginUpdate/EndUpdate, или dirty-состояние.** Приложение отмечает начало и завершение изменений в БД. Пока есть незавершённые обновления, кэш может возвращать старое значение, `WAIT` или `MISS`. В предложении со счётчиком последний `EndUpdate` снимает dirty. Что после этого возвращает `Get latest`, зависит от отдельного решения:

- **Оставить прежнее значение.** `Get latest` по-прежнему может его вернуть. Если после чтения этого значения данные в БД изменились, завершение обновлений само по себе не восстановит свежесть.
- **Инвалидировать текущее значение.** Следующий `Get latest` получит `MISS`, если кэш ещё не заполнен заново. Приложение прочитает БД. Кэш должен отличать это заполнение от опоздавшей записи, которая прочитала БД до commit.
- **Записать значение через `EndUpdate`.** Следующий `Get latest` получит записанную версию без дополнительного чтения БД. Для этого кэш должен получить актуальное подтверждённое значение: последний доставленный `EndUpdate` мог относиться к более раннему commit или к rollback.

Это варианты для обсуждения. Ни один из них сам по себе не решает потерю `EndUpdate`, commit после таймаута или непрерывный поток обновлений без выхода из dirty.

**Эксклюзивная блокировка до обновления БД.** Клиент получает `Lock(key)` до начала изменения в БД. Другой писатель того же ключа ждёт. После commit первый клиент вызывает `Put` со значением, токеном блокировки и `operationId`; кэш проверяет токен, сохраняет версию и освобождает блокировку за одну операцию. Пока все писатели соблюдают протокол и блокировка действует, `Put` приходят в порядке обновлений БД. Два предела гарантии: клиент может упасть между commit и `Put`; транзакция может завершиться уже после истечения блокировки. В первом случае версия не попадёт в кэш, во втором прежний клиент всё ещё способен изменить БД. [Обязательная сериализация всех обновлений (R-010)](../REQUIREMENTS.md#r-010) отвергнута: это рассмотренная альтернатива, а не требование к приложениям.

**Lease на заполнение после MISS.** Один читатель получает токен и загружает значение из БД. Для остальных обсуждались два варианта: вернуть `WAIT` с повторным чтением или временно отдавать предыдущее значение, если контракт допускает устаревший ответ. Второй вариант требует отдельно определить, можно ли вернуть старое после инвалидации и как долго. Известное кэшу изменение ключа отменяет токен и не даёт опоздавшему заполнению затереть новое значение. Lease можно сочетать с инвалидацией, но он не блокирует писателей БД и не обнаруживает commit, о котором кэш ещё не знает. E-009.

**CAS с перечитыванием или инвалидацией при конфликте.** Использует доступный примитив PoC, но успешный CAS всё ещё может принять старый снимок БД. Такой вариант допустим только с явно ограниченной гарантией или с дополнительным протоколом.

| Механизм | От какой гонки защищает | Какие ограничения остаются | Что требуется от приложения |
|---|---|---|---|
| Инвалидация после commit | После принятого события кэш перестаёт выдавать прежнее значение как latest. | Между commit и событием возможен старый ответ. Само событие не блокирует опоздавший `Put`. | После commit обеспечить доставку события об изменении ключа. |
| `BeginUpdate` / `EndUpdate` | Даёт кэшу возможность на время изменений не выдавать прежнее значение и отклонять заполнения, начатые до изменения БД. | Сам счётчик ничего не запрещает. После снятия dirty нужны правила для latest и опоздавших заполнений. Таймаут не доказывает, что транзакция завершилась. | Отмечать начало и исход каждого обновления, включая rollback. |
| Эксклюзивная блокировка | Пока блокировка действует, два писателя одного ключа не могут выполнить commit и `Put` в разном порядке. | Сбой между commit и `Put`, поздний commit после истечения блокировки. [Обязательная сериализация отвергнута](../REQUIREMENTS.md#r-010). | Все писатели берут `Lock` до изменения БД и передают токен в `Put` после commit. |
| Lease на заполнение | Пока lease действует, только один читатель получает право заполнить ключ. Известное кэшу изменение отменяет это право, и запоздалое заполнение отклоняется. | Lease не обнаруживает commit в БД без уведомления и не блокирует писателей. | Заполнять ключ с выданным токеном и обрабатывать `WAIT`, если выбран такой ответ. |
| CAS с обработкой конфликта | Отклоняет `Put`, если ревизия кэша уже изменилась с момента, когда клиент её прочитал. | Успешный CAS не доказывает свежесть данных из БД. | Передавать ожидаемую ревизию; при конфликте заново читать БД или инвалидировать значение. |

Ни один вариант пока не выбран. Внутреннее обсуждение связывает строгую гарантию с доставляемым уведомлением после обновления либо уведомлением до него при известной верхней границе выполнения. Это выявленное условие проектирования, а не согласованное обязательство клиента и не доказательство конкретного алгоритма. E-008, E-009.

## Повторы и неизвестный исход

Для каждой операции нужно различить отказ до применения и потерю ответа после возможного применения. Один gRPC-код ошибки без серверного контракта не устанавливает эту границу.

Можно автоматически повторять только гарантированный отказ до предложения записи. Другой вариант — разрешить [повтор неоднозначной записи по operationID](../REQUIREMENTS.md#r-011) и хранить её исходный результат атомарно с эффектом. Это требует срока хранения дедупликации, поведения после восстановления и передачи результата в другой регион. Третий вариант оставляет клиенту явный unknown outcome и процедуру сверки. Эти политики можно сочетать для разных операций, но нужно определить общий deadline, лимиты попыток gateway и повторы самого клиента.

## Сценарии, различающие решения

1. Читатель получает старую БД до чужого commit и заполняет кэш после него. Проверить, может ли latest стать старым и как долго это допустимо.
2. Put применён, ответ потерян, затем меняется лидер и приходит повтор. Проверить число эффектов и то, может ли клиент восстановить исходный результат. Для варианта с lease и дедупликацией повторить запрос с тем же `operationId` после использования одноразового токена: пока исходный результат хранится, повтор должен вернуть его, а не `STALE` из-за уже использованного токена. В предложении этого добиваются проверкой `operationId` до проверки токена. E-009.
3. DB-транзакция переживает lease/dirty timeout; затем следует поздний commit. Повторить при непрерывных writers без свободного окна.
4. Удалить current при сохранённой old и прочитать latest/explicit old. Повторить после TTL, вытеснения и restart с потерей служебных метаданных.
5. Повторить operationID в другом регионе до доставки исходной операции. Проверить связь дедупликации с позицией репликации из RFC-003.
6. Для dirty-состояния завершить два обновления одного ключа и доставить `EndUpdate` не в порядке commit. Отдельно завершить последнее обновление через rollback после успешного commit другого. После снятия dirty проверить ответ `Get latest` и результат опоздавшего заполнения, которое прочитало БД до commit.

## Условия закрытия

Нужно согласовать допустимую staleness, полноту истории, Get response, Delete current и обязанности приложения. Если выбран dirty-протокол, нужно определить, что становится latest после последнего `EndUpdate` и какие заполнения после этого допустимы. Для выбранного протокола описать состояния и атомарные переходы, сроки жизни lease, маркеров и operationID, затем выполнить сценарии и контрактные тесты. Численные пределы пока не установлены. Владелец решения и срок не назначены этим документом.
