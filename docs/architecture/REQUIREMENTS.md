# Требования к OraCache

<a id="требования-области-действия-и-приёмка"></a>
<a id="области-и-статусы"></a>

OraCache — распределённый кэш профилей и данных соцграфа. Его задача — ускорить чтение и снизить нагрузку на основную БД. БД остаётся источником данных.

## Границы выпуска

- <a id="r-005"></a>**R-005. Исходный минимум MVP:** заполнение при промахе, инвалидация по событиям, версии записей, репликация между двумя логическими регионами и метрики попаданий и задержки. Окончательный состав выпуска ещё не согласован. [Постановка проекта](../initial-task.md#обязательная-часть-базовый-состав-проекта-и-mvp).

<a id="реестр"></a>

## Требования к продукту

### Чтение и версии

- <a id="r-001"></a>**R-001. Чтение при промахе.** Если значения в кэше нет, кэш сообщает о промахе. Приложение само читает значение из БД и записывает его в кэш. Кэш не обращается к БД при обработке `Get`. [Cache-aside](adr/ADR-001-cache-aside.md).
- <a id="r-028"></a>**R-028. Назначение версии.** Когда кэш принимает новое значение по `Put`, он сам присваивает ему номер версии и возвращает этот номер клиенту. Клиент не задаёт этот номер. Он обозначает версию значения в кэше, а не порядок изменений в основной БД. [Контракт версий](rfc/RFC-001-api.md#понятия-и-установленные-ограничения).
- <a id="r-006"></a>**R-006. Выбор версии.** Клиент может прочитать текущую версию ключа или указать номер нужной версии. Если запрошенной версии нет, кэш сообщает об этом, а не подставляет текущую. Вместе со значением клиент получает список сохранённых версий этого ключа.
- <a id="r-007"></a>**R-007. История версий.** Число версий, которые кэш хранит для одного ключа, задаётся в настройках. Если лимит достигнут, при записи новой версии кэш удаляет самую старую версию этого ключа. В историю попадают только значения, записанные в кэш; изменения в БД могут в ней отсутствовать.
- <a id="r-008"></a>**R-008. Удаление версии.** Для `Delete` клиент указывает ключ и обязательный номер версии. Кэш удаляет только эту версию. Остальные версии ключа остаются доступными по своим номерам. Что вернёт запрос текущей версии после её удаления, пока не решено.
- <a id="r-012"></a>**R-012. Срок хранения.** Срок жизни записей (TTL) настраивается. Чтение любой сохранённой версии ключа продлевает срок жизни всех его сохранённых версий. [Продление TTL в другом регионе](rfc/RFC-002-ttl.md).

### Изменения в основной БД

- <a id="r-025"></a>**R-025. Инвалидация по событию.** При изменении данных в БД кэш получает событие по подписке и помечает прежнее значение как неактуальное или удаляет его. Источник событий можно заменить. [Требование заказчика](../initial-task.md#инвалидация).
- <a id="r-009"></a>**R-009. Защита от отката.** Если приложение прочитало из БД старое значение и записывает его в кэш с опозданием, оно не должно заменить уже закэшированное новое значение. Для случая, когда ключ после инвалидации ещё пуст, допустимость устаревшего ответа и его срок не согласованы. Целевой контракт должен явно определять гарантии свежести. [Гонки при заполнении](rfc/RFC-001-api.md).
- <a id="r-010"></a>**R-010. Подключение к приложению.** Для интеграции достаточно подключить клиент OraCache и вызывать его методы. Менять архитектуру приложения или схему основной БД не требуется. Защита от отката не должна требовать монотонного номера ревизии в БД или выполнения всех обновляющих `Put` строго по очереди.

### Регионы и доступ к данным

- <a id="r-027"></a>**R-027. Число регионов.** Архитектура должна поддерживать произвольное число регионов и несколько экземпляров хранилища в каждом. Два региона — минимум из исходной постановки MVP, а не предел системы. [Топология](../initial-task.md#топология).
- <a id="r-002"></a>**R-002. Один регион записи.** В каждый момент только один регион вправе принимать изменения от приложения. Запрос на запись из другого региона направляется в регион записи. [Решение о регионе записи](adr/ADR-002-write-region.md).
- <a id="r-017"></a>**R-017. Прогрев.** Система поддерживает массовую загрузку данных, в том числе после потери всех копий. При загрузке из источника с нуля достаточно одной версии на ключ. Оператор может запустить прогрев вручную. К моменту включения экземпляра в балансировку на нём уже должны быть данные, необходимые для обслуживания запросов. [Прогрев кэша](../initial-task.md#прогрев-кэша).
- <a id="r-026"></a>**R-026. Балансировка.** Система распределяет запросы между готовыми экземплярами. Добавление готового экземпляра или вывод работающего не требуют ручной перенастройки балансировщика. [Балансировка](../initial-task.md#балансировка).
- <a id="r-018"></a>**R-018. Восстановление после сбоя.** После отказа система должна восстанавливать данные. Если у шарда уцелело большинство реплик, потерянную реплику можно заменить, сохранив подтверждённые записи. Если до сбоя регион обязался доставить изменение, после восстановления он должен выполнить это обязательство: одной перезагрузки значений из БД недостаточно. Для потери большинства и полного падения допустимые потери и способ восстановления ещё не согласованы. [Сценарии восстановления](rfc/RFC-003-recovery.md#сценарии-восстановления).

- <a id="r-029"></a>**R-029. Региональное чтение.** Приложение может читать данные из копии в своём регионе. Для таких чтений нужно выбрать модель свежести: либо ограничить отставание, либо гарантировать, что после прекращения изменений и восстановления связи копии сойдутся. Гарантия чтения при обрыве межрегиональной связи пока не согласована. [Региональные гарантии](rfc/RFC-003-recovery.md).

## Принятые архитектурные решения и ограничения

- <a id="r-003"></a>**R-003. Шарды и реплики.** Ключи распределены по шардам. У каждого шарда в регионе три реплики (RF3), которые согласуют изменения по протоколу Raft. [Решение о трёх репликах](adr/ADR-003-rf3.md).
  - **Размещение в Kubernetes.** Заказчик требует одинаковых конфигураций pod хранилища. Отдельный pod для каждой реплики — вариант команды. Требование заказчика не запрещает одному pod хранить реплики разных шардов.
- <a id="r-015"></a>**R-015. Межрегиональная репликация.** Регион записи передаёт изменения в другие регионы асинхронно через очередь исходящих событий (outbox). В какой момент запись подтверждается клиенту, пока не определено. [Межрегиональная репликация](rfc/RFC-003-recovery.md).
- <a id="r-020"></a>**R-020. Маршрутизация.** Шлюз направляет запросы к репликам. Control Plane (CP) предоставляет сведения о топологии. Лидера шарда выбирает сама Raft-группа. Как шлюз находит адреса и сколько может пользоваться старой картой, если CP недоступен, ещё не решено. [Управление топологией](rfc/RFC-004-topology.md).

## Что ещё не согласовано

| Тема | Открытый вопрос | Где обсуждается |
|---|---|---|
| Версии и свежесть | Как нумеровать версии после удаления ключа? Нужна ли отдельная операция для удаления всего ключа? Должны ли значение и список версий в ответе соответствовать одному моменту времени? Каков лимит истории по умолчанию? | [API](rfc/RFC-001-api.md) |
| <a id="r-011"></a>R-011. Повтор записи | Если ответ потерялся, как клиент узнает результат? Временное право на заполнение и идентификатор операции — предложения, а не обещание однократного выполнения. | [Повторы и гонки](rfc/RFC-001-api.md) |
| <a id="r-013"></a>R-013. Нехватка памяти | Какие данные можно не принимать или вытеснять? Насколько после этого может различаться содержимое региональных копий? | [TTL и вытеснение](rfc/RFC-002-ttl.md) |
| <a id="r-016"></a>R-016. Отказ региона | Какие записи допустимо потерять и как долго сервис может оставаться недоступным? Как передать право записи, чтобы вернувшийся регион не начал принимать записи одновременно с новым? | [Региональные отказы](rfc/RFC-003-recovery.md) |
| <a id="r-021"></a>R-021. Изменение размещения | Как заменить реплику работающего шарда? Такая замена не меняет владельца ключа. Изменение числа шардов с переносом ключей — отдельная операция; её выполнение без остановки кластера не входит в базовое предложение. | [Состав и размещение](rfc/RFC-004-topology.md) |
| Размещение и прогрев | Как разнести три реплики по независимым машинам или площадкам? Какие данные нужны новому экземпляру до включения в балансировку? | [Топология](rfc/RFC-004-topology.md), [восстановление](rfc/RFC-003-recovery.md) |

<a id="как-принимать-результат"></a>

## Нагрузка и метрики

- <a id="r-022"></a>**R-022. Сравнение с работой без кэша.** Эффект кэша оценивается по задержке клиентского запроса и числу чтений из БД на одинаковой нагрузке. В оценку затрат входят процессор, память, сеть и диск всего стенда, включая CP и шлюз. Исходный профиль — 10 000 чтений и 500 записей в секунду при размере записи «10кб». Это условия испытания, а не результат замера. Точный размер в байтах, длительность и ресурсные бюджеты пока не согласованы. [Профиль нагрузки](../initial-task.md#профиль-нагрузки).
- <a id="r-023"></a>**R-023. Метрики.** Нужны доля попаданий в кэш, p95 и p99 задержки, доля устаревших ответов. Последняя зависит от того, какой ответ считается устаревшим по выбранной модели свежести. По состоянию реплик и маршрутов оператор должен отличать потерю связи с CP от потери большинства в Raft-группе. Целевые пороги и инструменты мониторинга пока не выбраны. [Постановка](../initial-task.md#особенности-тестирования-и-метрики).

## Условия сдачи проекта

- **Стенд и демонстрация.** Проект запускается по инструкции в чистом окружении. В демонстрации участвуют приложение, кэш и тестовая БД с генератором изменений. Для испытаний задана [структура записи «Пользователь»](../initial-task.md#структура-данных-для-тестирования); это не ограничение на формат значений клиентского API.
- **Испытания.** В отчёте нужны результаты для популярных ключей и одновременных промахов, потери событий и падения региона. Потеря уведомления из БД и пропуск изменения на пути между регионами — разные сценарии. [Ожидаемые результаты и измерения](../initial-task.md#какой-результат-хотим-получить).
- **Обоснование технологий.** Команда объясняет выбор компонентов и показывает, какую нагрузку выдерживает одна единица развёртывания и сколько ресурсов ей нужно. [Готовые технологии допустимы](../initial-task.md#переиспользование-технологий), если в проекте достаточно самостоятельной работы для команды из шести человек.

## Что показал прототип (PoC)

- <a id="r-004"></a>**R-004. Стенд.** Один регион, один шард, три процесса хранилища в памяти, заранее заданный состав Raft-группы, CP и шлюз. [Границы эксперимента](adr/ADR-004-poc.md).
- <a id="r-024"></a>**R-024. Смена лидера.** После остановки лидера две оставшиеся реплики выбрали нового, клиент продолжил работу через тот же шлюз. Это не проверка отказа региона или производительности. [Интеграционный эксперимент](experiments/single-shard-integration.md), [отчёт о проверках](experiments/static-leader-verification.md).
- <a id="r-014"></a>**R-014. Отличия от целевого API.** В проверенном прототипе чтение не продлевало TTL, `Get` возвращал одно значение без списка версий, а после удаления текущей версии текущей могла стать предыдущая. Автоматическое истечение TTL не входило в PoC.
- <a id="r-019"></a>**R-019. Потеря памяти.** Работающая реплика может догнать группу с помощью снимка. Снимок в оперативной памяти не обеспечивает безопасного возврата реплики, которая потеряла состояние, под её прежним идентификатором.
