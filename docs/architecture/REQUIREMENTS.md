# Требования, области действия и приёмка

## Области и статусы

Target — конечное продуктовое решение. PoC — интеграционный эксперимент: один регион, один шард, три storage-процесса, CP/gateway и хранение в памяти. MVP — промежуточный выпуск, единый состав которого пока не согласован. Уменьшение PoC не отменяет требований target.

Номер требования остаётся постоянным при изменении формулировки. В колонке статуса отдельно названы установленное положение и открытые детали. Сценарий проверки — критерий будущей приёмки, если рядом не указан конкретный выполненный запуск. Наличие реализации не означает согласование решения; уверенность в свидетельстве не равна его полномочиям утверждать продукт.

Прямое уточнение владельца E-017 подтверждает Raft, шарды и асинхронную межрегиональную репликацию с outbox. Финальный CP/discovery остаётся открытым. Сохранены предметно установленные cache-aside, single write-region, RF3 и требование TTL. Технические термины и путь запроса объяснены в [обзоре](ARCHITECTURE.md).

## Как принимать результат

Для PoC можно использовать только результаты конкретных срезов и запусков. Их границы изложены в [отчёте проверок](experiments/static-leader-verification.md). Успешная смена лидера не проверяет [список версий в ответе Get (R-006)](#r-006), [поведение после удаления последней версии (R-008)](#r-008) или [возврат потерявшей память реплики (R-019)](#r-019). В проверенном API Get возвращает одно значение, а после удаления последней версии предыдущая может снова стать последней.

Для MVP сначала требуется зафиксировать состав: выбранные R-ID, исключения, критерии остановки и открытые RFC, которые допускается отложить. Затем проверяется именно этот состав.

Для target нужны согласованные протоколы и измеримые критерии [нагрузки (R-022)](#r-022) и [наблюдаемости (R-023)](#r-023). Старые расчётные примеры не являются результатами измерений. Этот реестр не назначает владельцев и сроки и не устанавливает SLO без основания.
