# OraCache: архитектура и открытые решения

OraCache — распределённый версионный кэш перед основной базой данных приложения. Он хранит ограниченную историю значений ключа и должен поддерживать работу в нескольких регионах. Основная БД остаётся источником данных: при отсутствии значения приложение читает БД и заполняет кэш.

Этот пакет предназначен инженеру, который впервые знакомится с проектом. Здесь описаны принятые положения, вопросы проектирования и уже выполненный интеграционный эксперимент. Подробности эксперимента не задают окончательное устройство продукта.

**Что можно запустить сейчас.** В [`main` на 18 ноября 2026 года](https://github.com/OraCache/OraCache/blob/842cca19950c6aba5a9ced467ca9d1a5fd641213/README.md) клиент обращается прямо к трём узлам Store + Raft. Control Plane и gateway для этого не нужны. Полный путь через gateway проверяли отдельно в интеграционном PoC.

## Что уже определено

Для конечного решения выбраны cache-aside, единый регион записи и RF3 — три реплики данных. Владелец отдельно подтвердил применение Raft, шардирование и асинхронную межрегиональную репликацию через outbox. Шардирование делит ключи на группы; Raft согласует изменения между репликами группы; outbox хранит события для последующей доставки в другой регион. Выбор этих механизмов не закрывает их клиентские и отказные контракты. Основания: E-001, E-002, E-003, E-017.

Control Plane (CP) — управляющая часть системы — пока служит временной рабочей основой интеграции. Окончательные устройство CP и способ service discovery, то есть получения адресов доступных сервисов и реплик, не утверждены. Текущий статический вариант с подсказками о лидере реализован и имеет свидетельства проверок, но остаётся экспериментом. E-017, E-018.

## Как понимать статусы

- **Target** обозначает конечное продуктовое решение. Принятое положение target может ещё не иметь реализации.
- **PoC** обозначает узкий эксперимент интеграции: один регион, один шард, три storage-процесса, CP и gateway, хранение в памяти.
- **MVP** обозначает промежуточный выпуск. Единого согласованного состава MVP пока нет; его нужно выбрать явно из требований target.
- **RFC** нужен, когда предстоит выбор. Он может меняться в ходе обсуждения и сравнивать уже работающие варианты. Когда вопрос решён, указываем итог и ссылку на ADR, если выбор архитектурно значим.
- **ADR** фиксирует, что выбрали, для какой области и с какими последствиями. Он может появиться после RFC или непосредственно из явной договорённости. Опечатки и ссылки можно исправлять. Если меняется сам выбор, пишем новый ADR, а прежний помечаем как заменённый со ссылкой на новый. Ошибочную запись о якобы принятом решении исправляем явно.
- **Реализовано** относится к конкретному срезу кода; **проверено** — к конкретному запуску. Ни одно из этих слов само по себе не означает согласования архитектуры или приёмки продукта.

[Отчёт существующих проверок](experiments/static-leader-verification.md) отделяет срезы и запуски. Новых runtime-проверок эта редакция документов не добавляет. E-015, E-016, E-018.

Основания E-001…E-018 перечислены в [индексе](EVIDENCE-INDEX.json). Это устойчивые ключи к отдельно хранимой трассировке. Для понимания текста доступ к частному архиву не нужен; прямые цитаты, участники и частные локаторы в пакет не включены. [Правила публикации](PUBLISHING.md) описывают эту границу.
