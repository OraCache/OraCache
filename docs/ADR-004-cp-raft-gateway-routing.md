# ADR-004. Маршрутизация Gateway к реальным Raft-репликам

Статус — предложено для интеграции #35 и #36.

## Решение

Контракт #37 и live-view #67 остаются базой от upstream. Из #65 используется
правило монотонного Raft term для каждой пары регион–партиция. Из
[Gateway forwarding](https://github.com/OraCache/petruekhin-vibe/pull/2)
и [application layer](https://github.com/OraCache/petruekhin-vibe/pull/1)
перенесены ограниченная пересылка запросов и агент внутри `storage-node`.
Модель размещения, клиентский протокол и Store + Raft из #68 переиспользуются.

В `GetConfig` снимок для Gateway содержит наблюдаемый term, конфликт
лидерства и реплики, подтвердившие готовность в этом term. Адреса остаются в
статической топологии. Изменение наблюдений не меняет `config_revision`.
Gateway помнит максимальный term для той же Raft-группы в рамках жизни
процесса. Если отчёты нового term истекли, готовность снимается и маршрут
к прежнему term не возвращается. Конфликт сохраняется до большего term.

Gateway выбирает готового лидера и при необходимости пробует другие
подтверждённые реплики той же партиции и региона. При отказе CP сохраняется
последняя принятая карта. Когда CP доступен и очередной отчёт исключил
реплику, она также исключается из резервных попыток. Подсказка
`NOT_LEADER` должна ссылаться на готовую реплику с допустимым адресом и
term. Получив её, Gateway запрашивает обновление карты отдельно от запроса.
Успешная пересылка позволяет запомнить адрес, пока наблюдение CP и
конфигурация актуальны.

Storage Node подтверждает право обслужить строгий запрос через локальный
Raft. При включённом CP Agent клиентская запись дополнительно требует
последней принятой конфигурации, активного назначения и master-региона.
Запись повторяется только после отказа `NOT_LEADER` до её передачи в Raft.
Если клиентский RPC вернул `Unavailable` или `DeadlineExceeded`, итог
записи может быть неизвестен и Gateway возвращает исходную ошибку.

## Границы

Интеграционный стенд проверяет одну статическую Raft-группу и хранит состояние
в памяти. При замене Raft-группы новой инкарнацией под той же парой
регион–партиция потребуется идентификатор инкарнации в конфигурации.
Персистентная карта, динамический состав, TLS и репликация между регионами
остаются последующими срезами.
