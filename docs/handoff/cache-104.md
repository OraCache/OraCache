# cache-104: согласованный план изменения состава Raft-группы через CP

Статус: требования уточнены в обсуждении 25–26 ноября 2026 года. Реализация не начата. Этот документ не меняет поведение системы.

## Цель и границы

Дать административному клиенту возможность изменять состав конкретной Raft-группы по пути «клиент → API Gateway → лидер группы» через отдельный gRPC API и поддерживать в Control Plane (CP) актуальную проекцию фактического состава для маршрутизации. Фактическое членство определяет только Raft: изменение предлагает лидер группы, CP отражает уже применённый состав и состояние готовности нод, но не назначает участников работающей группы. Отдельного механизма pull, с помощью которого CP опрашивает лидера за составом, в согласованном варианте нет.

«Всегда актуален» не является гарантией при асинхронной сети: между применением записи Raft и доставкой heartbeat возможна задержка. CP должен различать подтверждённое свежее наблюдение и устаревшее либо неизвестное состояние.

## Текущее состояние репозитория

- shardraft.Instance и internal/node.Node предоставляют AddLearner, PromoteLearner, RemoveNode, Replace и общий ChangeMembership. Операции соответствуют add-learner, promote, remove, replace. Лидер подтверждает кворум через ReadIndex, предлагает ConfChangeV2; реплики меняют состав при применении подтверждённой записи.
- Новая нода запускается с новым PeerID и NodeID, прежним GroupID и флагом --join. Она не делает Bootstrap. AddLearner включает её без права голоса; отдельный PromoteLearner допускается после проверки RecentActive и Match >= Commit. Replace повышает уже догнавшего learner и удаляет старого voter через joint consensus. Для изменения нужен кворум прежней группы. Успех add-learner подтверждает членство, но не окончание синхронизации.
- Ручка GET/POST /membership находится на Raft HTTP listener storage-ноды. POST адресуется лидеру, проверяет group_id и передаёт MembershipChange. GET возвращает локальное наблюдение, которое может отставать. У ручки сейчас нет аутентификации.
- internal/node.Node сейчас отклоняет любое изменение состава при подключённом CP Agent (--cp-addr), чтобы Raft и размещение CP не разошлись.
- Клиент cmd/oracache и gRPC CacheGateway содержат команды для данных кэша, но не для membership. cmd/api-gateway обслуживает CacheGateway и получает маршруты из CP.
- CP Config хранит NodeID, клиентский Address и для каждой партиции ReplicaNodeIDs. У него нет PeerID и RaftAddress. Текущий live-view выводит готовность и лидера только среди назначенных ReplicaNodeIDs; heartbeat новой ноды сам по себе не меняет размещение.
- В Raft PeerID — числовая идентичность участника группы; NodeID — идентичность приложения/CP. Address (ClientAddr) — клиентский gRPC адрес, RaftAddress (RaftURL) — отдельный HTTP адрес для сообщений Raft. Использованный PeerID нельзя повторно выдать новой пустой ноде.

## Принятая модель ответственности

- Административный клиент задаёт намерение изменить состав и operation_id. Только текущий лидер группы проверяет условия и предлагает изменение Raft. Gateway находит группу и лидера и передаёт запрос; при смене лидера использует ответ NotLeader для обновления направления.
- Raft остаётся источником истины о фактическом составе: voter, learner, outgoing voter, удалённые участники. CP строит проекцию применённого состава и использует отдельные heartbeat для живости и готовности. CP не делает ноду участником Raft своим назначением и не считает ноду членом Raft только потому, что получил от неё heartbeat.
- Исходная конфигурация CP может задавать bootstrap группы и сведения об узлах, но после запуска не управляет её фактическим членством. Статическое назначение и наблюдаемый состав Raft должны оставаться различимыми данными; изменение одного не должно неявно переписывать другое.
- Состояние learner видно CP, но learner не попадает в клиентские маршруты. Готовые voter могут использоваться для маршрутизации с учётом фактического лидера. Желаемое размещение, если оно понадобится CP как управляющему компоненту, следует хранить отдельно от фактического состава Raft.

## Публикация состава: три согласованных триггера

Использовать расширенный ReportHeartbeat, содержащий полный снимок применённого состава для группы. Отправитель снимка — действующий лидер.

1. Сразу после применения каждой подтверждённой конфигурационной записи лидер инициирует внеочередной heartbeat с полным составом. Для joint consensus допускается публикация промежуточного состояния с признаком joint; после auto-leave публикуется конечное состояние.
2. После вступления в роль лидера и применения доступных подтверждённых записей новый лидер инициирует heartbeat с полным составом. Триггер — смена лидерства, а не каждый отдельный голос на выборах.
3. Каждый обычный heartbeat лидера также содержит полный состав. Он исправляет потерю внеочередного сообщения и восстанавливает представление CP после перезапуска, без отдельной ручки pull. Периодичность берётся из существующего механизма heartbeat.

Ни один сетевой сбой CP не откатывает уже подтверждённое изменение Raft. Внеочередная публикация повторяется либо заменяется следующим heartbeat с более новым полным снимком. Сообщение должно отражать применённую конфигурацию, а не намерение, неприменённый proposal или локальный список seed-адресов.

## Данные и обработка в CP

Передавать идентичность группы и её инкарнации (GroupID), регион и партицию, PeerID/NodeID отправителя, term, индекс последней применённой конфигурации (configIndex), признак joint, полный список участников с PeerID, NodeID, ролью voter/learner/outgoing voter, клиентским и Raft адресами. При необходимости передавать removed IDs для диагностики и защиты от повторного использования идентичности. Поля лидерства и живости не должны входить в сравнение содержимого конфигурации при равном configIndex: лидер может смениться без изменения состава.

CP хранит полный снимок состава для группы, сопоставляет его с текущим GroupID и применяет снимки по монотонному configIndex. Меньший индекс игнорируется; равный индекс с тем же составом идемпотентен; равный индекс с иным составом — ошибка согласованности. Term и наблюдаемого лидера CP обновляет отдельно от состава. Новая инкарнация GroupID должна проходить отдельную проверку привязки к региону и партиции, а не смешиваться со старым индексом. При принятии отчёта CP обновляет свою проекцию и публикуемую для Gateway ревизию/представление так, чтобы маршруты не использовали старый список реплик.

В конфигурации CP не переопределять молча смысл существующего `ReplicaNodeIDs` как фактического membership: сейчас это статическое назначение. Ввести отдельную проекцию применённого состава, а клиентские маршруты строить по её готовым voters и актуальному лидеру. Нового участника с его `NodeID`, `PeerID`, клиентским и Raft адресами нужно представить в публикуемом Gateway состоянии так, чтобы проверка конфигурации и разрешение адреса не отвергали его. После удаления участник не должен оставаться в маршрутах лишь из-за старого назначения.

Проверку записей на storage-ноде согласовать с новой моделью: действующий voter, в том числе повышенная новая нода, не должен получать `FailedPrecondition` из-за отсутствия в прежнем статическом `ReplicaNodeIDs`. При этом сохранить проверку master-региона и запрет записи для learner/удалённой ноды; окончательное право предлагать запись по-прежнему проверяет Raft.

Heartbeat от неизвестной ноды можно принять как наблюдение для диагностики, но он не добавляет её в состав или маршруты. Для каждого участника CP отдельно учитывает свежесть heartbeat, роль и Ready. При отсутствии свежих подтверждений лидера CP помечает лидерство как неизвестное/устаревшее; CP не заявляет, что сохранённый снимок обязательно совпадает с текущим составом Raft.

## Административный путь и операции

- Добавить в административный клиент команды для add-learner, promote, remove, replace и просмотра состава; передавать GroupID, operation_id и нужные идентификаторы/адреса. Клиент использует gRPC, как и для операций с кэшем.
- Ввести отдельный gRPC-сервис управления составом на Gateway и storage-ноде, сохранив `CacheGateway` и его существующие методы/сообщения для Get/Put/Delete без изменений. Оба сервиса могут работать на уже существующих клиентских gRPC listeners. Gateway определяет группу по явной идентичности в запросе и адресует её текущему лидеру; для этого CP должен публиковать клиентский gRPC адрес участника. При `NotLeader` Gateway может использовать подсказку с клиентским gRPC адресом лидера, проверив, что адрес принадлежит запрошенной группе.
- Сохранить семантику operation_id: после timeout, разрыва соединения или смены лидера клиент повторяет тот же запрос с тем же ID и содержимым; повтор не создаёт новую конфигурационную запись. Не делать автоматический повтор после исхода, который мог быть commit, с новым ID.
- После появления сверки CP с применённым составом снять запрет dynamic membership при --cp-addr. Пока сверка не реализована, запрет сохраняется.
- Аутентификация сейчас отсутствует во всей системе; добавление её в новый административный API не входит в эту задачу. Существующий HTTP `/membership` может остаться для совместимости, но клиентский путь через Gateway использует новый gRPC-сервис.

## Совместимость существующих контрактов

- Расширять protobuf-сообщения CP новыми полями без изменения номеров и смысла существующих полей. Отдельный gRPC-сервис membership добавляется к существующим сервисам; старые вызовы `CacheGateway` сохраняют сигнатуры и формат ответов.
- Сохранить разделение статического размещения, фактического состава Raft и текущей готовности. CP и Gateway должны получать достаточно данных для нового маршрута, но прежние потребители статической конфигурации не должны принять наблюдаемый состав за назначение CP.
- Сохранить ограничение пользовательских записей master-регионом, существующие правила Raft для quorum и promotion, а также дедупликацию по `operation_id`. При обновлении узлов разных версий новый административный сервис доступен только там, где он реализован; совместимость смешанных версий должна быть проверена отдельно.

## Восстановление и проверки

- Потерян внеочередной push: очередной полный heartbeat лидера восстанавливает CP.
- Лидер сменился до публикации или во время доставки: новый лидер после применения подтверждённых записей и затем периодически публикует полный состав. Сообщение старого лидера не должно откатить более новый configIndex или актуальное лидерство.
- CP перезапустился: после следующего успешного heartbeat лидера он восстанавливает фактический состав; до этого состояние отмечено как неподтверждённое. Если используется постоянное хранилище, сохранённый состав всё равно сверяется по heartbeat.
- В CP пришли дубли, сообщения не по порядку либо одинаковый индекс с разным составом: обработка по правилам configIndex выше.
- Новая нода присылает heartbeat до add-learner: CP не маршрутизирует на неё запросы. После add-learner она видна как learner, после promote и подтверждения готовности может попасть в маршруты.
- Replace/remove проходят через joint consensus; CP не должен преждевременно считать промежуточное состояние конечным. После auto-leave маршруты отражают конечный состав.
- При потере связи CP с Raft-группой гарантии мгновенной актуальности нет; CP показывает устаревшее/неизвестное состояние вместо ложного подтверждения.

## Update — 26 ноября 2026

В рабочей копии реализован сквозной путь управления составом Raft-группы через Gateway. Ревью подтвердило штатный сценарий и выявило дефекты в обработке запоздавших сообщений, восстановлении маршрутов и совместимости версий.

### Что реализовано

- `ReportHeartbeat` передаёт полный применённый состав группы от лидера. Снимок включает `GroupID`, регион, партицию, `PeerID` отправителя, `configIndex`, `joint`, участников с их ролями и адресами, а также удалённые `PeerID`. `NodeID` отправителя и `term` передаются в существующих полях heartbeat.
- Внеочередной heartbeat инициируется при применении изменений состава и при смене лидерства. Каждый обычный heartbeat лидера также содержит полный снимок. Подтверждение Raft-операции зависит от её применения в Raft, а публикация в CP выполняется асинхронно.
- CP хранит наблюдаемый состав отдельно от статического `ReplicaNodeIDs`. Меньший `configIndex` пропускается при обновлении снимка, равный индекс с тем же составом принимается идемпотентно, равный с другим составом вызывает ошибку. Привязку `GroupID` можно изменить обновлением статической конфигурации. Live-view выставляет `Confirmed` по свежему наблюдению лидера.
- Gateway получает обновлённый live-view при той же ревизии топологии и строит клиентские маршруты по готовым voters и наблюдаемому лидеру. Обычный heartbeat неизвестной ноды сохраняется для диагностики. Learner виден в составе, а повышенный voter входит в маршруты после подтверждения готовности. Конечный состав после auto-leave отражает удаление или замену участника.
- Отдельный сервис `MembershipAdmin` работает на существующих клиентских gRPC listeners Gateway и storage-ноды. CLI поддерживает `membership get`, `add-learner`, `promote`, `remove` и `replace`. Gateway выбирает кандидатов по группе и проверяет адрес из `NotLeader` по её составу. Дедупликацию по `operation_id` выполняет Raft. При неопределённом исходе Gateway возвращает ошибку, и клиент может повторить тот же запрос с тем же ID.
- Снят запрет изменения состава с `--cp-addr`. Storage-нода проверяет master-регион и собственную роль по применённому составу Raft, поэтому новый voter может обслуживать записи вне bootstrap-списка. Реализация использует прежний контракт `CacheGateway` и сохраняет HTTP `/membership` для совместимости.

Gateway затем сравнивает `term` новой группы с `term` прежней по региону и партиции. Если `term` новой группы ниже, готовый лидер получает `ErrNoLeader`. Воспроизведены обе стадии. [MemoryStore](../../internal/statestore/memory.go#L165) · [Router](../../internal/gateway/router.go#L265)
2. **[P1] Запоздавший heartbeat снимает подтверждение актуального лидера.** Устаревший снимок пропускается, но его heartbeat перезаписывает статус отправителя. Live-view сбрасывает `Confirmed` и клиентские маршруты до следующего свежего отчёта. Воспроизведено для меньшего `configIndex` и для меньшего `term` при равном индексе. [Приём heartbeat](../../internal/statestore/memory.go#L91) · [Подтверждение состава](../../internal/statestore/live.go#L94)
3. **[P1] После рестарта CP Gateway сохраняет прежнюю карту во время прогрева.** Свежий CP при совпадающей ревизии отвечает без live-view. Gateway продолжает использовать прежнюю карту, которая может содержать уже удалённого участника. По согласованному сценарию CP должен отдать неподтверждённое состояние до первого свежего снимка лидера. [GetConfig](../../internal/cpapi/server.go#L292) · [Poller](../../internal/gateway/poller.go#L97)
4. **[P1] Совпадение `NodeID` подменяет адрес маршрута другой группы.** Проекция membership перезаписывает глобальный `Nodes[].Address` по одному `NodeID`. Воспроизведено, как публикация learner в одном регионе меняет клиентский адрес готового лидера в другом. Разрешение адреса участника должно учитывать конкретную группу. [Проекция адресов](../../internal/statestore/live.go#L23) · [Разрешение маршрута](../../internal/gateway/router.go#L290)
5. **[P2] Старый Gateway отклоняет live-view после повышения нового voter.** Старый валидатор требует, чтобы `ready_replica_node_ids` и `leader_node_id` ссылались на статический `replica_node_ids`. Новый CP публикует в этих полях фактических готовых voters и лидера. Проверка с валидатором до правок подтвердила `invalid config` для снимка с новым лидером. При поэтапном обновлении старый Gateway сохранит прежнюю карту. [Валидация](../../internal/cpconfig/config.go#L266) · [Применение live-view](../../internal/gateway/poller.go#L107)

### Предлагаемая модель маршрутизации

Raft определяет фактический состав группы. CP ведёт наблюдения и публикует готовую карту маршрутов с `GroupID` и адресами участников. Gateway применяет карту CP и хранит её для работы при недоступности CP. Порядок Raft `term` и `configIndex` учитывает CP в пределах одной инкарнации. `NotLeader` может ускорить обновление карты из CP.

- При смене привязки `GroupID` CP исключает heartbeat прежней группы из расчёта и публикует `unknown` для затронутой партиции до свежего подтверждения новой группы. Порядок обновлений нужно проверять и для снимка состава, и для статуса отправителя. Иначе запоздавший heartbeat всё ещё сможет снять подтверждение актуального лидера.
- CP разрешает клиентские адреса в контексте группы и включает их в готовую карту. Это исключает перезапись маршрутов других групп через общий `Nodes[]` при совпадении `NodeID`.
- Версия карты должна меняться при изменениях состава или готовности даже при прежней ревизии статической топологии. Если ответы могут прийти в другом порядке, Gateway сравнивает версии карт CP. Правило сравнения должно учитывать рестарт CP.
- Успешный ответ CP заменяет состояние группы в Gateway. Явный `unknown` снимает прежний маршрут, в том числе во время прогрева после рестарта CP. При недоступности CP Gateway может использовать последнюю полученную карту в пределах согласованной политики свежести. Возраст маршрута отсчитывается от последнего подтверждения лидера. Повторная выдача того же наблюдения свежесть не продлевает.
- Для готовой карты стоит предусмотреть версионируемый формат или отдельный RPC. При поэтапном обновлении динамические изменения состава можно включать после перехода Gateway на новый контракт, чтобы старый валидатор не отклонил весь live-view.

**Открытый вопрос — допустимость записей по кэшу при смене `GroupID`.** Если Gateway потерял связь с CP до переключения, то по сохранённому маршруту он может отправить запись в прежнюю группу. При живом кворуме эта группа способна подтвердить запись. Строгое переключение потребует остановить приём операций прежней группой или дождаться истечения её права обслуживать старый маршрут. При обычной смене лидера в том же `GroupID` действуют проверки лидерства и кворума Raft.
