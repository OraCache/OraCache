Предварительное архитектурное и бюджетное планирование

## 1. Исходные требования и допущения

| Параметр               | Значение                                                                                 |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| Полезный объём данных  | 100 GB                                                                                   |
| Средний размер объекта | 10 KB                                                                                    |
| Нагрузка               | 10 000 read RPS + 500 write RPS                                                          |
| Целевая latency        | около 5 ms; percentile и точка измерения не заданы                                       |
| RAM узла               | 64 GB                                                                                    |
| Eviction               | Включён; политика требует уточнения                                                      |
| Топология              | Один primary-регион для чтения/записи, остальные регионы — только чтение                 |
| Репликация             | Полная копия данных в каждом регионе, плюс холодная реплика каждого шарда внутри региона |

## 2. Расчёт памяти и количества узлов

Примем плановую модель полезной ёмкости узла:

$$  
M_{\text{payload}}=\frac{M_{\text{node}}\times K_{\text{payload}}}{U_{\text{reserve}}}  
$$

Где $M_{\text{node}}=64$ GB, $K_{\text{payload}}=0{,}70$ — доля RAM, доступная под полезные данные с учётом ОС и накладных расходов, $U_{\text{reserve}}=1{,}20$ — дополнительный запас на пики, фрагментацию и фоновые операции.

$$  
M_{\text{payload}}=\frac{64\times0{,}70}{1{,}20}  
\approx37{,}3\text{ GB/узел}  
$$

Коэффициенты — плановые допущения, а не универсальные константы. Фактический расход зависит от числа ключей, структур данных, аллокатора, репликации, AOF/RDB и copy-on-write при создании снимков.

Для одной копии:

$$  
N_{\text{copy}}=  
\left\lceil\frac{100}{37{,}3}\right\rceil=3  
$$

Трёх узлов достаточно только по суммарной ёмкости: это не доказывает возможность безопасного размещения primary и replica с запасом при отказе узла.

Для выбранного примера принимаем **3 шарда × 2 узла на шард = 6 узлов на регион**. Дла каждого шарда — отдельная холодная реплика на разных физических серверах. 

|Размещение|Расчёт|Узлы|
|---|---|---|
|Один регион|$S\times2=3\times2$|6|
|Все регионы|$R\times S\times2=3\times3\times2$|18|
|Память всей системы|$18\times64$ GB|1 152 GB|

Для других значений число узлов рассчитывается как $N=2RS$, если каждый шард имеет один primary и одну отдельную холодную реплику. При отказе узла реплика должна иметь возможность принять роль primary.

## 3. Выбор конфигурации серверов

Рекомендуемый базовый профиль: **16 физических ядер / 32 потока, 64 GB RAM, 2 × 2 TB NVMe**. CPU выбирается по сочетанию производительности одного ядра и запаса для фоновых задач, а не путём прямого пересчёта RPS в ядра.

|Профиль|CPU: физические ядра / потоки|Диски на узел|Применение и ограничения|
|---|---|---|---|
|Экономичный|8 / 16|2 × 1 TB NVMe|Низкая стоимость; меньше запаса для восстановления и persistence|
|**Базовый — рекомендован**|**16 / 32**|**2 × 2 TB enterprise NVMe**|Баланс производительности, надёжности и стоимости|
|Производительный|24 / 48|2 × 3,84 TB enterprise NVMe|Для подтверждённой высокой CPU-нагрузки, интенсивного persistence или более быстрого восстановления|

Два диска рекомендуются для зеркалирования RAID1: отказ одного накопителя не должен приводить к потере локального набора persistence. Полезная ёмкость зеркала из двух дисков по 2 TB — приблизительно 2 TB десятичной ёмкости до форматирования. Диски нужны для ОС, журналов AOF, снимков RDB и восстановления; больший объём сам по себе не увеличивает RPS. Выносливость записи, IOPS и задержку необходимо проверить на реальной persistence-нагрузке.

| Итоговый профиль узла         | Значение                                    |
| ----------------------------- | ------------------------------------------- |
| CPU                           | AMD EPYC, класс 16 ядер / 32 потока         |
| RAM                           | 64 GB ECC                                   |
| Диски                         | 2 × 2 TB enterprise NVMe, RAID1             |
| Плановая полезная ёмкость RAM | 37,3 GB по модели выше                      |
| Назначение                    | Основная нода шарда или ее холодная реплика |
| Ограничение                   | 5 ms latency не гарантируется без benchmark |

## 4. Нагрузка и сеть

При условном размере объекта 10 KB:

$$  
T_{\text{read}}=10,000\times10\text{ KB}  
=100\text{ MB/s}\approx800\text{ Mbit/s}  
$$

$$  
T_{\text{write}}=500\times10\text{ KB}  
=5\text{ MB/s}\approx40\text{ Mbit/s}  
$$

Это полезный трафик без протокольных заголовков, ответов другого размера, служебного трафика и пиков. При распространении каждой записи из primary-региона во все остальные регионы:

$$  
T_{\text{replication}}\approx(R-1)\times5\text{ MB/s}  
$$

Для $R=3$ это около 10 MB/s, или 80 Mbit/s, исходящего межрегионального полезного потока. Реальная репликация может передавать больше данных из-за формата протокола, служебных операций и повторной синхронизации.

Шардирование распределяет данные и нагрузку, но средние $RPS/S$ не гарантируют равномерности: горячие ключи, неравномерные размеры объектов и распределение команд могут перегружать отдельные шарды. Сеть 10 Gbit/s не следует обосновывать только средним трафиком: выбор интерфейсов зависит от пиков, восстановления, репликации и сетевых гарантий площадки.

## 5. Latency и нагрузочное тестирование

До production deployment провести тесты с реальным распределением ключей, размерами значений и целевой нагрузкой.

| Проверка                      | Критерий принятия решения                                                                          |
| ----------------------------- | -------------------------------------------------------------------------------------------------- |
| Устойчивая и пиковая нагрузка | 10 000 read RPS и 500 write RPS; отдельно проверить запас выше пика                                |
| Latency                       | p50, p95, p99; уточнить, означает ли 5 ms p95 или p99 и измеряется ли время на клиенте или сервере |
| CPU                           | Нет устойчивой перегрузки одного ядра; сохраняется запас для фоновых операций                      |
| RAM и eviction                | Нет непредусмотренного вытеснения, OOM и опасной фрагментации                                      |
| Репликация и отказ            | Измерены replication lag, время переключения и полного восстановления                              |
Выводы по результатам тестирования
1. **Оставить базовый CPU**, если тесты подтверждают требуемые percentile latency, достаточный запас CPU и стабильную работу persistence. 
2. Перейти на производительный профиль, если ограничителем выступают CPU, производительность одного ядра или фоновые операции. 
3. Увеличивать RAM, если полезная ёмкость недостаточна либо требуется больший запас для восстановления. 
4. Дисковую конфигурацию менять только при подтверждённом ограничении IOPS, выносливости записи или времени восстановления.

## 7. Предварительный бюджет

Актуальные опубликованные цены проверены **29 октября 2026 г.** как ориентир, не как коммерческое предложение. Например, в каталоге [OVHcloud](https://www.ovhcloud.com/) представлены серверные конфигурации от $354/месяц для класса Advance-4, но конкретная комплектация и цена могут отличаться от выбранного профиля.

Для бюджетирования примем **$350–600 за узел в месяц**. Это предварительный диапазон для планирования, а не подтверждённая цена сервера с нужными RAM, дисками и сетевыми условиями.

|Статья|Один регион (6 узлов)|Система (18 узлов)|
|---|---|---|
|Узлы в месяц|$2 100–3 600|$6 300–10 800|
|Узлы в год|$25 200–43 200|$75 600–129 600|
|Первоначальная настройка|По коммерческому предложению|По коммерческому предложению|

Стоимость рассчитывается по формуле:

$$  
C_{\text{total}}=  
N_{\text{nodes}}\times C_{\text{node}}+  
C_{\text{network}}+  
C_{\text{operations}}+  
C_{\text{setup}}  
$$

Сеть, межрегиональный трафик, мониторинг, обслуживание, backup и первоначальная настройка не включены в приведённую стоимость узлов. 
Bare metal удобен для предсказуемого размещения и контроля оборудования; собственные серверы требуют отдельного учёта закупки, амортизации, запасных частей, площадки, питания и персонала. 
Для окончательного сравнения нужны одинаковые SLA, география, сетевые лимиты и стоимость эксплуатации.

## 8. Итоговая рекомендация

Для предварительного планирования принять **16 физических ядер / 32 потока, 64 GB ECC RAM и 2 × 2 TB enterprise NVMe RAID1 на узел**. Для иллюстративного сценария из трёх регионов и трёх шардов на регион заложить **18 узлов**, ориентировочно **$6 300–10 800 в месяц без дополнительных расходов**.

Перед production deployment необходимо подтвердить:
1. Фактический объём данных с накладными расходами кеша и долю памяти, необходимую для безопасного восстановления.
2. Количество регионов и шардов, размещение реплик и поведение при отказе узла.
3. Percentile и точку измерения целевой latency 5 ms.
4. Результаты benchmark CPU, RAM, дисков, persistence и репликации.
5. Допустимый replication lag, достижимость RPO/RTO и восстановление из независимого backup.
6. Коммерческие цены, сетевые лимиты, стоимость межрегионального трафика и эксплуатации.

**Решение о production sizing принимать после нагрузочного тестирования.** Приведённые количества и бюджет — расчётная базовая модель, а не гарантия производительности или отказоустойчивости.
