# Gateway: интерфейс пользователя

Описание протокола из [`proto/cache/gateway.proto`](../proto/cache/gateway.proto). Здесь — что умеет gateway и примеры запросов и ответов в JSON.

## Коротко

Пользователь (сервис профилей, CLI, тесты) знает один адрес и не видит, сколько регионов и нод за ним стоит. Gateway сам выбирает ближайший живой регион.

| Метод | Что делает |
|---|---|
| `Get` | Прочитать профиль: последнюю версию или конкретную |
| `Put` | Записать новую версию профиля. Номер версии назначает кеш |
| `Delete` | Удалить одну версию или все версии ключа |
| `BatchGet`, `BatchPut` | То же пачкой, до 1000 штук |

## Главные правила

- Версию назначает кеш при `Put` и возвращает её в ответе.
- У ключа хранится несколько версий — по умолчанию 3, лимит настраивается. Когда приходит четвёртая, самая старая удаляется.
- Инвалидация = `Put` новой версии или `Delete`.Отдельного метода `Invalidate` нет.
- TTL продлевается при каждом `Get` — сразу у всех версий ключа.
- Потолок срока жизни: версия удаляется по потолку, даже если её постоянно читают. Так данные не живут вечно, если обновление потерялось.
- `Put` и `Delete` реплицируются во второй регион.
- Cache-aside: при промахе пользователь сам читает источник и кладёт результат через `Put`.

## Формат JSON

Примеры ниже — в стандартном JSON-представлении protobuf:

- имена полей: `expected_rev` → `expectedRev`;
- числа `uint64` (номера версий) — строкой: `"rev": "5"`;
- даты — строкой в UTC: `"2026-10-30T12:00:00Z"`;
- `data` — профиль, упакованный в байты и закодированный в base64. В примерах вместо base64 стоит пометка вида `<Profile v5>`.

Сам профиль выглядит так:

```json
{
  "fullName": "Иван Петров",
  "age": 30,
  "sex": "SEX_MALE",
  "registeredAt": "2024-05-12T10:00:00Z",
  "city": "Москва"
}
```

## Get

### 1. Есть в кеше — отдаём последнюю версию

Запрос:
```json
{ "key": "profile:42" }
```
Ответ:
```json
{
  "status": "GET_STATUS_HIT",
  "rev": "5",
  "data": "<Profile v5>",
  "latestRev": "5",
  "expiresAt": "2026-10-30T12:05:00Z",
  "hardExpiresAt": "2026-10-30T12:30:00Z",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```
`rev == latestRev` — отдана последняя версия. `expiresAt` уже сдвинут: чтение продлило TTL.

### 2. Нет в кеше — промах (cache-aside)

Запрос:
```json
{ "key": "profile:77" }
```
Ответ:
```json
{
  "status": "GET_STATUS_MISS",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```
Дальше пользователь читает профиль из источника и кладёт его в кеш — см. [Put, сценарий 1](#1-первая-запись-после-промаха).

### 3. Конкретная (предыдущая) версия

Запрос:
```json
{ "key": "profile:42", "rev": "4" }
```
Ответ:
```json
{
  "status": "GET_STATUS_HIT",
  "rev": "4",
  "data": "<Profile v4>",
  "latestRev": "5",
  "expiresAt": "2026-10-30T12:05:00Z",
  "hardExpiresAt": "2026-10-30T12:28:00Z",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```
`rev < latestRev` — отдана не последняя версия.

### 4. Запрошенной версии уже нет

Хранятся только последние 3 версии; версия 1 уже вытеснена.

Запрос:
```json
{ "key": "profile:42", "rev": "1" }
```
Ответ:
```json
{
  "status": "GET_STATUS_VERSION_NOT_FOUND",
  "latestRev": "5",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```

### 5. Ближайший регион недоступен — ответил другой

Запрос тот же, что в сценарии 1. Регион A лежит, gateway переключился на B:
```json
{
  "status": "GET_STATUS_HIT",
  "rev": "5",
  "data": "<Profile v5>",
  "latestRev": "5",
  "expiresAt": "2026-10-30T12:05:00Z",
  "hardExpiresAt": "2026-10-30T12:30:00Z",
  "servedBy": { "region": "region-b", "instance": "cache-b-1", "failover": true }
}
```
Для пользователя ничего не меняется; `failover: true` нужен для метрик и диагностики.

## Put

### 1. Первая запись после промаха

`expectedRev: "0"` — Если кто-то успел записать раньше, наши данные могут быть старее, то кеш не примет их.

Запрос:
```json
{
  "key": "profile:77",
  "data": "<Profile>",
  "expectedRev": "0"
}
```
Ответ:
```json
{
  "status": "PUT_STATUS_OK",
  "rev": "1",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```

### 2. Профиль изменился — новая версия

Пользователь знает, что последняя версия — 5, и записывает изменения поверх неё.

Запрос:
```json
{
  "key": "profile:42",
  "data": "<Profile: город поменялся на Казань>",
  "expectedRev": "5"
}
```
Ответ:
```json
{
  "status": "PUT_STATUS_OK",
  "rev": "6",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```
Теперь у ключа версии 6, 5, 4; версия 3 удалена по лимиту. Запись уходит во второй регион.

### 3. Конфликт — кто-то записал раньше

Медленный клиент тоже отталкивался от версии 5, но версия 6 уже есть.

Запрос:
```json
{
  "key": "profile:42",
  "data": "<Profile: старые данные>",
  "expectedRev": "5"
}
```
Ответ:
```json
{
  "status": "PUT_STATUS_CONFLICT",
  "rev": "6",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```
Старые данные не стали последней версией. Клиент может перечитать версию 6 и решить, что делать.

### 4. Запись без проверки

Если `expectedRev` не указан, кеш записывает без проверки. Удобно для тестов, но защиты от опоздавших записей нет.

Запрос:
```json
{ "key": "profile:42", "data": "<Profile>" }
```
Ответ:
```json
{
  "status": "PUT_STATUS_OK",
  "rev": "7",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```

### 5. Слишком большая запись

Профиль больше 10 КБ.

Ответ:
```json
{
  "status": "PUT_STATUS_TOO_LARGE",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```

## Delete

### 1. Удалить одну версию

Запрос:
```json
{ "key": "profile:42", "rev": "6" }
```
Ответ:
```json
{
  "status": "DELETE_STATUS_DELETED",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```
Последней версией снова становится 5. Удаление уходит во второй регион, и версия 6 не «воскреснет» оттуда.

### 2. Удалить ключ целиком

`rev: "0"` (или поле не указано) — удалить все версии.

Запрос:
```json
{ "key": "profile:42" }
```
Ответ:
```json
{
  "status": "DELETE_STATUS_DELETED",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```

### 3. Повторное удаление

Запрос тот же. Ключа уже нет:
```json
{
  "status": "DELETE_STATUS_NOT_FOUND",
  "servedBy": { "region": "region-a", "instance": "cache-a-1" }
}
```
повтор безопасен, клиент может смело повторять `Delete` при сбоях сети.

## BatchGet

Запрос:
```json
{
  "items": [
    { "key": "profile:42" },
    { "key": "profile:77" }
  ]
}
```
Ответ — в том же порядке, что запрос:
```json
{
  "items": [
    { "status": "GET_STATUS_HIT", "rev": "5", "data": "<Profile v5>", "latestRev": "5" },
    { "status": "GET_STATUS_MISS" }
  ]
}
```
`BatchPut` устроен так же: статус по каждой записи, пачка не «всё или ничего».

## Жизнь одного ключа

| Действие | Версии в кеше | Последняя |
|---|---|---|
| `Get` → MISS | — | — |
| `Put` (expectedRev 0) | 1 | 1 |
| `Put` (expectedRev 1) | 2, 1 | 2 |
| `Put` (expectedRev 2) | 3, 2, 1 | 3 |
| `Put` (expectedRev 3) | 4, 3, 2 — версия 1 удалена по лимиту | 4 |
| `Delete` rev 4 | 3, 2 | 3 |
| `Delete` (весь ключ) | — | — |

## Срок жизни

TTL — 5 минут *(значение для примера, настраивается)*, потолок — 30 минут *(предложение)*.

| Время | Событие | TTL до | Потолок |
|---|---|---|---|
| 12:00 | `Put` версии 5 | 12:05 | 12:30 |
| 12:04 | `Get` | 12:09 | 12:30 |
| 12:08 | `Get` | 12:13 | 12:30 |
| … | читают каждые 4 минуты | … | 12:30 |
| 12:30 | потолок | — | версия удалена |
| 12:31 | `Get` → MISS, данные заново из источника | | |

Без потолка версию, которую постоянно читают, никто бы не удалил.

## Ошибки

Кроме статусов в ответе, gateway может вернуть ошибку gRPC:

| Код | Когда |
|---|---|
| `UNAVAILABLE` | Не отвечает ни один регион. Можно повторить позже |
| `INVALID_ARGUMENT` | Пустой ключ или в пачке больше 1000 элементов |
