# ADR-007. Подтверждение состава Raft для маршрутизации

Статус — контракт источника и режим изменения состава обсуждаются в #101.
Изменения CP и тесты находятся в интеграционной ветке #105/#107.

## Источники

Raft владеет членством. CP наблюдает завершённые конфигурации, сохраняет их
в StateStore и публикует через существующий GetConfig. Desired placement
остаётся в исходном assignment. Операторский путь изменения состава
относится к #104.

Источник для CP возвращает полную конфигурацию с идентичностью региона,
партиции и инкарнации группы. Он аутентифицирует ответившую реплику и
сверяет, что именно она является лидером. Лидер выполняет quorum ReadIndex
и ждёт локального apply. Смена лидера или терма во время чтения требует
новой проверки. Локальный `GET /membership` из #101 предназначен для
диагностики. В частности, ответ отставшего follower может содержать старый
состав и идентификатор лидера.

## Публикация

CP сверяет идентичность группы, терм, индекс изменения состава и список
voter из подтверждения с предыдущей записью. Переходная конфигурация
`joint=true` ждёт завершения. Адреса для Gateway берутся из доверенного
реестра нод CP. Подтверждённый состав и допуск публикуются одной ревизией
снимка. В etcd сравнение ревизии защищает от параллельной публикации,
а сохранённый индекс защищает от регрессии при рестарте.

Новому voter нужен свежий heartbeat с тем же `group_id` и индексом состава,
текущим термом и готовностью после apply. Если подтверждение состава
завершилось ошибкой, новый heartbeat сам по себе не откроет маршрут.
Существующие назначения продолжают использовать правила live-view. Gateway
пробует адреса готовых реплик из карты, в том числе после `NOT_LEADER`.
Storage Node получает подтверждённый состав через обычный GetConfig и
сохраняет проверку master-региона на записи.

Адрес `/metrics` берётся из метки развёртывания. Сбор метрик идёт на
уровне процесса независимо от членства в одной партиции. Роль learner
берётся из применённой конфигурации локальной Raft-реплики.

## Проверки

- `integration/e2e/check-dynamic-shard.sh` запускает standalone Raft
  с Prometheus и Grafana. Реальная команда `add-learner` включает node-4.
  Скрипт проверяет статус цели, роль learner в запросе из дашборда,
  отказ чтения прямо с learner, продвижение и удаление. Во втором Compose
  проекте Gateway выполняет PUT через CP, а лидер отклоняет ту же команду
  из-за включённого CP Agent. Оба проекта удаляются после прогона.
- `go test ./internal/gateway -run TestGatewayAdmitsVoterAfterConfirmedMembershipAndFreshReadiness`
  проверяет CP, GetConfig и клиент Gateway с заглушками подтверждения
  состава и RPC Storage Node. Проверяются learner, подсказка `NOT_LEADER`,
  неполный heartbeat, таймаут подтверждения, `servedBy` после смены лидера
  и отказ отката карты.
- `go test -tags=integration ./cmd/cp-api -run 'TestEtcdControlPlane/confirmed_membership_survives_cp_restart'`
  пересоздаёт CP API и клиент к реальному etcd. Заглушка источника после
  рестарта возвращает более ранний индекс. CP сохраняет опубликованную
  ревизию и подтверждение.

## Совместная приёмка

Нужны согласованный read-only RPC к текущему лидеру и операторский режим,
который разрешает изменение членства при включённом CP Agent. Текущий
`FailedPrecondition` из #101 сохраняется. После согласования:

1. Поднимите Raft с CP Agent, CP API с одним etcd namespace, Gateway и
   мониторинг. Через Gateway запишите значение и сохраните ревизию.
2. Запустите node-4 с собственным `/metrics` и тем же `group_id`.
   Выполните `add-learner` через согласованный операторский путь. Проверьте
   появление цели и роли learner без рестарта Prometheus. Проверьте,
   что Gateway игнорирует `NOT_LEADER` с её адресом.
3. Продвиньте догнавшую реплику. Дождитесь публикации CP после проверки
   свежего heartbeat. Переведите лидерство на node-4 разрешённой операцией
   или выборами с сохранением кворума. Тем же Gateway прочитайте исходную
   ревизию и выполните условный PUT. Оба ответа должны указывать
   `servedBy.instance=node-4` в master-регионе.
4. Перекройте один опрос состава, смените лидера и перезапустите CP API с
   тем же etcd. После восстановления проверьте индекс состава, чтение
   подтверждённого значения и условный PUT. Для перезапуска Storage Node
   с прежним Raft-состоянием требуется #108.
